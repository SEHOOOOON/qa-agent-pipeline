# 3-Tier QA 기준 및 적용 방식

본 문서는 파이프라인에서 Agent 2가 TC를 설계하고, Checkpoint 2가 이를 검증할 때 사용하는 핵심 품질 기준(3-Tier)을 정의합니다.

## 1. 3-Tier 기준과 요구사항의 우선순위 충돌 해결

3-Tier QA 기준은 기존 요구사항(SRS, Jira 등)을 대체하지 않습니다. 
Agent 1과 Checkpoint 1을 거쳐 승인된 **요구사항이 최상위 근거**가 되며, 3-Tier 기준은 누락된 테스트 관점을 찾고 TC를 구체화하는 보조 기준입니다.

> **💡 원칙**
> *   Tier 3 규칙과 요구사항 근거가 모두 있음 ➔ **Expected Result로 사용 확정**
> *   Tier 3에 규칙이 있지만 요구사항 근거가 없음 ➔ **Requirement Gap으로 반환 (임의 확정 금지)**

## 2. 3-Tier QA 품질 기준

### Tier 1. 공통 QA 기준 (Domain-Agnostic)
어떤 도메인의 시스템이더라도 기본적으로 확인해야 하는 재사용 가능한 범용 품질 기준입니다.
*   **정상 동작**: 정상 입력에서 전체 흐름이 완료되는가?
*   **예외 및 오류 처리**: 허용되지 않는 입력과 상태가 차단되는가?
*   **경계값**: 최솟값, 최댓값 및 범위를 벗어난 값이 구분되는가?
*   **복구와 초기화**: 상태 변경 후 원상 복구가 가능한가?
*   **권한과 접근 제어**: 권한이 없는 사용자의 실제 처리가 차단되는가?
*   **사용자 피드백**: 성공, 실패, 차단 사유가 UI에 명시적으로 표시되는가?

### Tier 2. 중앙제어 도메인 기준 (Domain-Specific)
다수의 장비를 동시에 감시하고 제어하는 '중앙제어 시스템' 특유의 품질 위험을 검토합니다.
*   **장비 식별 및 정확성**: 선택한 장비와 실제 제어 대상이 일치하는가?
*   **다중 장비 제어**: 다중 선택 장비 전체에 명령이 빠짐없이 적용되는가?
*   **비대상 장비 보존**: 미선택 장비의 상태가 명령 이후에도 유지되는가?
*   **정합성**: UI(화면) ↔ 내부 장치 상태(Memory) ↔ Register View(하드웨어 통신 대기열)가 완전히 일치하는가?
*   **부분 장애 격리**: 1대의 에러 장비가 정상 장비 제어에 영향을 주지 않는가?

### Tier 3. 관제점(기능)별 세부 품질 규칙 (Feature-Specific)
전원, 온도, 운전 모드 등 중앙제어의 각 관제점에 대한 구체적 정책 규칙입니다.

*   **온도**: 
    *   허용 범위: 16°C ~ 30°C
    *   차단 범위: 15°C, 31°C
    *   COOL/HEAT 모드: 온도 변경 가능
    *   FAN/DRY 모드: 온도 변경 불가 (변경 시 경고 표시 및 기존 값 유지)
*   **운전 모드**: 
    *   버튼 선택 ➔ 내부 상태(mode) ➔ Register 값 변경
    *   FAN/DRY 진입 시 온도 조작 제한
    *   COOL/HEAT 복귀 시 온도 변경 재허용
*   **통신 및 알람**: 
    *   Offline 상태 원격 명령 차단
    *   CH05, CH21 등 오류 코드 표시 시 정책적 제어 차단

## 3. Agent 2와 Checkpoint 2의 적용 방식

같은 3-Tier 기준을 공유하지만 역할이 철저히 분리됩니다.
*   **Agent 2**: 3-Tier 기준을 바탕으로 테스트 관점을 도출하고 TC 구조를 생성합니다.
*   **Checkpoint 2**: 생성된 TC가 ① 3-Tier 기준을 실제로 반영했는지, ② 요구사항 근거가 명확히 존재하는지, ③ 판정 가능하고 독립적인지(다른 TC에 의존하지 않는지) 검증합니다. (V1에서는 동일 ID/조건의 명시적 중복을 검토하고, V2에서는 의미론적 커버리지 분석을 수행합니다.)
