# 실무 도입 고려사항 (Production Adoption Considerations)

본 문서는 이 AI-assisted QA 파이프라인을 실제 비즈니스 및 엔터프라이즈 프로덕션(Production) 환경에 도입할 때 직면하게 될 현실적인 엔지니어링 한계점과 방어 전략을 다룹니다.

## 1. 무인 자율 릴리즈의 위험성 (Human Review)

포트폴리오(V1) 단계에서는 규칙 기반으로 자동 `PASS` 또는 `HOLD` 권고(Recommendation)를 도출하는 단계까지 구현되어 있습니다. 하지만 실무에서는 AI의 권고만으로 릴리즈를 강제 차단하거나 배포를 허가하지 않습니다.

*   **실제 판단 프로세스**: Agent 4가 5가지 원인 분류와 릴리즈 권고(PASS/HOLD)를 제공하면, 최종적으로 기획/QA 실무 담당자가 **APPROVE / REJECT / WAIVE**를 결정해야 합니다.
*   **만성 HOLD 위험성 방지**: 아주 사소한 에러나 덜 중요한 관제점의 실패 때문에 전체 배포가 지속적으로 차단(HOLD)되면, 조직에서 이 시스템의 알림을 양치기 소년처럼 무시하게 됩니다. 
    *   *해결 방향*: 기능의 중요도, Severity(심각도), 변경 위험도에 따라 예외 승인(WAIVE)을 처리할 수 있는 구조가 필요합니다.

## 2. AI 비결정성(Non-Determinism) 통제

동일한 기획서와 프롬프트를 입력하더라도 AI(Agent 1, Agent 2)의 출력 결과는 실행할 때마다 다를 수 있습니다. 이를 프로덕션 수준으로 제어하기 위해 다음 요소를 고정(Pinning)해야 합니다.

*   JSON Schema (구조와 필수 필드)
*   허용 가능한 상태값 Enum
*   ID 채번 규칙
*   프롬프트 버전 및 LLM 모델 버전 (예: `gpt-4-0613`처럼 특정 모델 버전을 명시)
*   결과물의 입력/출력 Hash 검증

## 3. 원인 분류의 모호성과 오차율

Timeout 에러 하나만 보더라도, 실제로는 1) 환경 불안정(environment_issue), 2) 잘못 작성된 자동화 코드(automation_issue), 3) 제품 자체의 무응답(product_defect) 중 어느 것인지 단번에 특정하기 어렵습니다.

*   **방어 전략**: Agent 4가 확신을 갖기 위해서는 Pre-check 결과, DOM 렌더링 상태 캡처, 최근 코드 변경 이력, 재실행(RERUN) 결과를 복합적으로 검토해야 합니다. AI의 분류 확신도(Confidence Score)가 기준치 미달일 경우, 시스템이 함부로 판정하지 않고 Human Review 큐(Queue)로 넘기는 구조가 필수적입니다.

## 4. 중복 이슈 억제 및 외부 보고 체계

동일한 결함이 발견될 때마다 Slack이나 Notion, Jira에 새로운 이슈 티켓으로 무한정 생성(Spamming)될 수 있습니다.

*   **방어 전략 (Upsert)**: 식별 가능한 고유 키를 기반으로 신규 생성(Insert)과 기존 이슈 업데이트(Update)를 구분하는 Upsert 로직이 필요합니다.
    *   `Run Key`: 프로젝트 + 브랜치 + Commit SHA + 실행 시각
    *   `Finding Key`: Requirement ID + TC ID + 실패 Signature (Error Stack)

## 5. 실무 도입 4단계 전략

실제 조직에 도입할 때는 한 번에 모든 권한을 주지 않고 다음 4단계에 걸쳐 권한을 위임합니다.

1.  **보조 도구**: AI는 요구사항 분석과 TC 설계 초안만 만들고 사람이 승인.
2.  **자동 실행 및 권고**: 승인된 TC를 실행하여 AI가 원인 분류 및 릴리즈 권고안을 제시하고 사람이 최종 결정.
3.  **제한적 자동 차단**: Pre-check 실패, JSON 불일치, Critical TC 실패 등 명백한 룰 위반 시에만 파이프라인이 자동 HOLD 처리.
4.  **선택적 자율화**: 방대한 운영 데이터가 쌓이고 AI 신뢰도가 입증된 후, 저위험 변경 사항에 한해서만 자동 승인 범위를 점진적으로 확대.
