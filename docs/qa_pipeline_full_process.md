# 중앙제어 Multi-Agent QA Pipeline

본 문서는 B2B 다중 장비 가상 관제 시스템을 대상으로 구성한 Multi-Agent QA 파이프라인의 단계별 역할, 품질 기준, 예외 처리 방식과 결과 전달 구조를 설명합니다.

---

## 1. 프로젝트 목표
이 프로젝트는 단순한 정상 동작 확인(Happy Path)을 넘어, 중앙제어 시스템의 복잡한 상태 전이와 다중 장비 제어 로직을 꼼꼼히 검증하는 것을 목표로 합니다.
AI 에이전트를 활용하여 요구사항을 분석하고, 승인된 테스트케이스(TC)를 Playwright로 실행하며, 결과를 정확하게 분류하는 일련의 프로세스를 구축했습니다.

---

## 2. 핵심 품질 기준

QA 파이프라인은 각 단계에서 다음 3단계 품질 기준을 순차적으로 적용합니다.

### 2.1 공통 QA 기준
- **정상·예외·경계값 분석**: 요구사항에 상·하한이 명시된 경우 경계값과 허용 범위 이탈 조건을 테스트케이스에 반영합니다.
- **상태 변경·회귀 영향**: 제어 전후의 상태 변화와 사이드 이펙트를 점검합니다.
- **정보 부족 여부 파악**: 요구사항이 명확하지 않은 경우, AI가 임의로 판단하지 않고 '정보 부족'으로 격리합니다.

### 2.2 중앙제어 도메인 기준
- **운전 모드별 제어 제한**: 송풍/제습 모드 등에서 온도 조절 버튼이 비활성화되는지 등 도메인 특화 동작을 검증합니다.
- **통신·알람·Lock 상태**: 통신 불량(CH05) 알람이나 전체 잠금 상태에서의 제어 차단 로직을 확인합니다.
- **다중 장비 제어와 상태 유지**: 복수 장비 제어 시, 비대상 장비의 비교 대상 필드(미선택 장비 상태)가 변경되지 않았는지 확인합니다.

### 2.3 기능별 품질 기준
- **적용 조건과 기대결과 명확화**: 실행 환경이 완비된 경우에만 기대값을 검증합니다.
- **통과·실패 판단 기준 확립**: 자동화 스크립트가 명확히 판별할 수 있는 논리적 기준을 설정합니다.
- **자동화 가능 범위 산정**: Playwright 등 UI 자동화 도구로 제어 가능한 범위를 식별합니다.

---

## 3. 전체 파이프라인

각 Agent의 결과가 다음 단계로 전달 가능한지를 확인하기 위해 **4단계 QA Checkpoint**를 적용합니다.

### Agent 1 + Checkpoint 1 (요구사항 정제)
- **역할**: 기능 목적과 예외 처리 기준이 모호한 요구사항을 분석하여 보완을 요청합니다.
- **분류**: 
  - `확정 정보`: 명세에 100% 명시된 사실.
  - `추정 정보`: 도메인 경험상 그럴듯하지만 명세에 없는 것.
  - `정보 부족`: Pass/Fail 판단에 필수이나 누락된 것.
- **Checkpoint 1 진행 판정**: 전체 진행, 일부 진행(Partial Proceed), 확인 후 진행(Hold)으로 나눕니다.

### Agent 2 + Checkpoint 2 (TC 설계)
- **역할**: Agent 1이 전달한 '확정 정보'와 '3단계 품질 기준'을 바탕으로 독립적인 TC를 설계합니다.
- **테스트 독립성**: 모든 TC는 초기 상태, Setup, Cleanup을 명시하여 이전 테스트의 잔여 상태가 다음 테스트에 영향을 미치지 않도록 합니다.
- **통합 TC (Integration TC)**: 다중 장비 제어 및 비대상 상태 유지 검증 시 사용합니다.
- **상태 계층 검증**: 사용자 UI 표시값과 브라우저 내부 가상 장치 상태(Register Simulator View)를 각각 확인하고 정합성을 검증합니다.

### Agent 3 + Checkpoint 3 (자동화 실행)
- **역할**: 승인된 테스트케이스(TC)를 Playwright로 자동 실행하고, UI와 내부 장치 상태를 확인해 실행 결과와 증거 수집
- **실행 대상**: Checkpoint 2를 통과하여 자동화가 가능하다고 판단된 TC만을 대상으로 합니다.
- **수집 데이터**: 실행 상태(EXECUTED, BLOCKED, SKIPPED), 화면 스크린샷, 렌더링 상태 로그.

### Agent 4 + Checkpoint 4 (결과 분석)
- **역할**: 실행 결과와 증거를 기준으로 실패 원인을 정밀하게 분류하고, 외부로 보고합니다.
- **외부 보고**: 분석된 결과를 읽기 쉬운 형식으로 정리하여 Report, Notion, Slack에 동일하게 전달합니다.

---

## 4. 실행 결과 분류

단순 실패가 아닌 원인에 기반하여 테스트 결과를 다음 5가지로 명확하게 분류합니다.

1. **제품 결함 후보**: 정상 실행 환경에서 실제값이 명시된 기대값과 다른 경우.
2. **요구사항 확인 필요**: 기대결과나 정책이 기획서에 누락되어 판정이 불가한 경우 (예: 특정 알람 시 색상 정책 부재).
3. **환경·시뮬레이터 문제**: 화면 로드, 초기화 실패, 가상 응답 지연 등으로 정상 검증이 불가능한 경우.
4. **자동화 코드 문제**: UI 화면 패널이 버튼을 가리는 등, 순수 자동화 스크립트 로직의 결함.
5. **조건 부족으로 미실행**: 선행 조건 데이터 미준비 등으로 실행 전 중단된 상태.

---

## 5. 추적성 구조

요구사항부터 품질 기준, 테스트케이스(TC), 자동화 코드, 그리고 최종 실행 결과까지 고유 ID로 연결하여, 결함 발생 시 원인을 즉각 추적할 수 있는 구조(Traceability)를 설계했습니다.

---

## 6. 구현 범위와 한계

현재 파이프라인에서 확인된 구현 범위와 향후 고도화 계획은 다음과 같습니다.

- **Slack 연동**: 테스트 결과의 Slack 알림 수신을 확인했습니다. 향후 최종 메시지에 실행 수치와 세부 분류를 고도화할 예정입니다.
- **Notion 연동**: 분석된 테스트 결과를 Notion DB에 등록(적재)하는 연동을 확인했습니다. TC ID 기반 중복 방지 및 갱신 로직은 추가 고도화 대상으로 관리합니다.
- **실행 환경의 한계**: 실제 H/W 모드버스 통신이 아닌 브라우저 가상 환경(시뮬레이터)을 대상으로 검증을 수행합니다.

---

## 7. 저장소 구조 및 부록

- `docs/`: QA 프로세스, 품질 기준 등 파이프라인의 핵심 설계 문서 모음.
- `tests/`: Pytest 및 Playwright 기반의 실제 검증 스크립트.
- `reports/`: 실행 결과에 대한 리포트(HTML/JSON) 및 분석 자료.
- `assets/`: 실행 과정에서 수집된 증거 스크린샷 및 시연 영상 자료.
- 기능 단위로 커밋 이력을 정리해 전체 파이프라인의 구현 과정을 확인할 수 있도록 구성했습니다.
