# 🚀 AI 자율 QA 파이프라인 (0 to 100 초정밀 세부 공정 백서)

본 문서는 B2B 다중 기기 모의 관제 시스템을 대상으로 구축된 **다중 에이전트 기반 자율 QA 파이프라인**의 모든 세부 로직, 예외 처리 기준, 그리고 각 에이전트의 내부 의사결정 알고리즘을 먼지 한 톨까지 기록한 최종 마스터 백서입니다.

---

## 🏁 Phase 0: 프로젝트 기반 사상 및 아키텍처 설계 (Core Philosophy)
기존 AI 기반 QA의 치명적 단점인 '환각(Hallucination)'과 '수박 겉핥기식 표면 검증'을 원천 차단하기 위해 **4단계 Gatekeeper 거버넌스**를 도입했습니다.

1.  **정보 부족 통제 (Information Insufficiency Control)**: 요구사항에 명시되지 않은 정보는 절대 AI가 상상해서 채우지 못하도록 통제.
2.  **독립성 보장 (State Isolation)**: 이전 TC의 잔여 상태가 다음 TC를 오염시키지 않도록 철저한 Setup/Cleanup 강제.
3.  **UI/Register 이중 검증 (Double-Assert)**: 프론트엔드 UI의 표시 값과 백엔드(시뮬레이터 Register)의 실제 데이터 무결성을 동시 교차 검증.
4.  **추적성 (Traceability)**: 기획서(Requirement) ➡️ 테스트케이스(TC) ➡️ 결함 티켓(Bug) 간의 1:1 양방향 추적성 보장.

---

## 🛡️ Phase 1: 요구사항 정제 및 통제 (Agent 1: Requirement Analyst)
**단순 파싱이 아닌, 요구사항의 결함을 찾아내고 반려(Hold)하는 '수석 기획/QA 분석가' 역할**

*   **세부 판정 알고리즘 (Level 1~3)**:
    *   `Level 1`: 기능 목적이나 패스 기준이 불명확함 ➡️ **[Hold]** 판정. 확정 TC 생성 불가.
    *   `Level 2`: 주요 동작은 있으나 예외 처리, 상태 전이가 누락됨 ➡️ **[Partial Proceed]** 판정. 명확한 부분만 진행.
    *   `Level 3`: UI 시나리오, 관제점, Register 매핑 완비 ➡️ **[Proceed]** 판정.
*   **정보의 엄격한 3분류 (가장 핵심적인 환각 통제 장치)**:
    *   `[확정 정보]`: 요구사항에서 100% 명시된 사실. **(오직 이 정보만 Agent 2의 Expected Result로 사용 가능)**
    *   `[추정 정보]`: 도메인 경험상 그럴듯하지만 명세에 없는 것. **(Agent 2 사용 절대 금지)**
    *   `[정보 부족]`: Pass/Fail 판단에 필수이나 누락된 것. **(기획자 확인 필요 대상으로 격리)**
*   **통합 검증(E2E) 필요성 자체 판단 로직**:
    *   단순히 관제점이 많다고 통합 검증을 지시하지 않음. "다중 기기에 일괄 명령을 전송하는가?", "공유 상태(Register)를 사용하는가?" 등 구체적 조건 충족 시에만 E2E 테스트를 지시.

## 🧪 Phase 2: 독립적 TC 설계 및 이중 검증 로직화 (Agent 2: TC Designer)
**Agent 1이 넘겨준 `[확정 정보]`만을 재료로, 코드로 즉각 변환 가능한 독립적 TC를 정밀 타격하듯 설계**

*   **TC 독립성(State Isolation) 강제**:
    *   모든 TC는 반드시 `[초기 상태(Initial State)]`, `[Setup]`, `[Cleanup]` 3단계를 명시해야 함. 이전 테스트가 남긴 쓰레기 데이터로 인해 다음 테스트가 실패하는 결함을 원천 차단.
*   **이중 검증(Double-Assert) 적용의 합리적 분기 처리**:
    *   에이전트가 마음대로 판단하는 것이 아니라, 아래 명확한 룰에 따라 기계적으로 분기:
        1.  `Double-Assert Required`: 제어/상태 변경 시 (UI 텍스트 검증 + Register 메모리 무결성 동시 검증)
        2.  `UI-only Allowed`: 단순히 UI 레이아웃, 버튼 노출 여부, 접근성 검증 시 (Register 무관)
        3.  `Register-only Allowed`: 백그라운드 스케줄링, 내부 초기화 검증 시 (UI 무관)
*   **Integration TC (다중 상태 오염 검증) 세부 룰**:
    *   복수 장비 제어 시, 제어 대상 장비의 값이 변경되었는지 확인하는 것에 그치지 않고, 반드시 **"비대상 장비(Non-target) 및 비대상 필드는 변경되지 않고 기존 값을 100% 유지함"**을 강제로 Assert 하도록 명시.
*   **중복 TC 통폐합 로직 (Duplicate Prevention)**:
    *   `Preconditions`, `Action`, `Expected UI`, `Expected Register` 네 가지 항목이 모두 동일한 TC는 무의미한 중복으로 간주하고 단일 TC로 병합 처리.

## 🤖 Phase 3: 브라우저 자동화 및 예외 분류 엔진 (Agent 3 & Playwright)
**사람의 개입 없이 100% 무인으로 브라우저를 조작하며, 단순 에러가 아닌 원인을 분석**

*   **구체적 실행 로직**:
    *   `test_controller.py`를 통해 Chromium 기반 Playwright 구동.
    *   `virtual-controller.html` 시뮬레이터 로드 후 DOM Element(UI)를 클릭/검증하고, 동시에 브라우저 내부 `localStorage` (가상 Register 메모리) 데이터를 뜯어내어 값 비교.
*   **에러 분류 엔진 (H/W Timeout vs S/W Bug)**:
    *   테스트 실패 시 무조건 "버그"라고 리포팅하지 않음.
    *   **`[S/W Bug]`**: 응답은 정상적으로 왔으나 값이 기대값과 불일치하는 경우 (소프트웨어 로직 결함).
    *   **`[H/W Timeout]`**: 명령을 내렸으나 네트워크 지연이나 장비 무응답으로 인해 타임아웃이 발생한 경우 (통신/하드웨어 결함)로 정밀하게 예외(Exception)를 분리하여 처리.

## 📢 Phase 4: CI/CD 결과 분석 및 영구 보존 리포팅 (Agent 4 & Notify Bot)
**수만 줄의 로그를 읽기 쉽게 정제하고, 이해관계자에게 실시간 전파**

*   **Notion DB 중복 적재 방지 (Upsert 로직)**:
    *   단순히 API로 행을 추가(POST)하는 것이 아니라, 기존 Notion DB에 해당 `TC_ID`가 이미 존재하는지 먼저 조회(GET).
    *   존재한다면 기존 데이터의 상태와 날짜만 업데이트(PATCH), 없다면 새로 생성(POST)하는 방어적 로직 구현.
*   **Slack 실시간 알림 포맷 고도화**:
    *   가독성을 위해 터미널 UI 포맷(Block Kit) 적용.
    *   전체 테스트 통과율(Pass Rate) 표시 및 Bug의 치명도(Critical/Major) 분류.
    *   가장 중요한 점: Agent 1이 발견한 **"요구사항 모호성(Ambiguity) 경고"**를 슬랙 최상단에 띄워 기획팀이 즉각적으로 스펙을 보완할 수 있도록 피드백 루프 형성.

## 🌟 Phase 100: 포트폴리오 자산화 및 구조 최적화 (The Masterpiece)
**이 모든 치열한 고민의 흔적들을 하나의 깔끔한 저장소에 박제**

*   **가상 시뮬레이터 정합성 (`virtual-controller.html`)**: 초기화(Reset) 시 16대 장비가 모두 완벽히 동일한 상태(`STOP`, 25.0도, `COOL` 등)를 갖도록 디폴트 배열 값을 동기화.
*   **아키텍처 회고록 (`ARCHITECTURE_TRADEOFFS.md`)**: Playwright를 선택한 이유(DOM 격리 및 실행 속도), 시뮬레이터 구조 등에 대한 시니어급 기술 부채 및 한계점 고찰.
*   **깔끔한 형상 관리**: 
    *   `docs/`, `tests/`, `reports/` 로 프로젝트 폴더 구조화.
    *   19개의 얽혀있던 영어 커밋들을 **"세부 로직과 히스토리를 완벽하게 보존하면서 각각의 커밋을 전문적인 한글 메시지로 재작성"**하여, 면접관이 소스코드 이력을 볼 때 프로젝트의 성장 과정을 투명하게 확인할 수 있도록 세팅 완료.
