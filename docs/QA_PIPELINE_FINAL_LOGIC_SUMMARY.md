# 🚀 QA 파이프라인 (Agent 1~4) 최종 로직 변천사 및 아키텍처 요약본

본 문서는 프로젝트 진행 과정에서 지속적으로 고도화된 Agent 1 ~ 4의 핵심 로직과 파이프라인의 아키텍처 변화를 상세히 기록한 **최종 로직 요약본**입니다. 추후 유지보수 시 각 컴포넌트의 역할과 판정 기준을 잊지 않기 위해 작성되었습니다.

---

## 🤖 Agent 1: 요구사항 분석 에이전트 (Requirement Analyst)
초기에는 단순히 스펙을 나열하는 수준이었으나, "명시되지 않은 기획의 빈틈"을 찾아내는 로직이 추가되었습니다.

*   **핵심 개선 로직: 모호성 감지 (Ambiguity Detection)**
    *   에러 발생 시 단순 에러 코드뿐만 아니라 UI 상의 구체적인 피드백(예: CH05 에러 시 카드 색상 변경 기준 등)이 문서에 정의되어 있는지 검증합니다.
    *   이 로직을 통해 **TC-07 (알람 발생 시 UI 색상 모호성)** 과 같은 기획 누락을 사전에 발견하고, `요구사항 확인 필요` 카테고리로 분류할 수 있게 되었습니다.

## 🤖 Agent 2: TC 설계 에이전트 (TC Designer)
문서 상의 TC와 실제 실행되는 코드 간의 괴리를 없애기 위해, 엄격한 네이밍 룰과 Boundary(경계값) 테스트 개념이 확립되었습니다.

*   **핵심 개선 로직: 식별자 통합 및 엣지 케이스 세분화**
    *   **식별자 통합**: `TC-01`, `TC-02` 식의 모호한 넘버링을 폐기하고, 목적이 드러나는 ID 체계(`TC-MODE-001`, `TC-ENV-000`, `TC-INT-002`)를 도입하여 문서-코드-리포트 간 100% 추적성을 확보했습니다.
    *   **경계값 검증(Boundary)**: 30°C 상한 초과 조작 시도 시 방어 로직(Toast 알림 및 값 롤백)을 TC에 명시적으로 추가했습니다.

## 🤖 Agent 3: 자동화 테스트 실행 (Pytest & Playwright)
단순 테스트 실행기를 넘어, 실행 결과의 신뢰성을 보장하고 풍부한 메타데이터를 수집하도록 `test_controller.py`와 `conftest.py`가 리팩토링되었습니다.

*   **핵심 개선 로직: Report 무결성 및 메타데이터 주입 (`conftest.py`)**
    *   **Pytest-HTML 버그 수정**: `pytest_html_results_summary` 훅을 오버라이딩하여, 상태(Skipped/Failed)에 따라 전체 실행 건수가 누락되던 버그(10건 -> 9건으로 표시되던 현상)를 픽스했습니다.
    *   **JSON 메타데이터 확장**: 단순 Pass/Fail 외에 `run_id`, `tc_id`, `executed_at`, `duration`, `evidence_path(스크린샷 경로)` 등 추적에 필요한 모든 데이터를 `qa_results.json`에 주입하도록 변경했습니다.

## 🤖 Agent 4 & Checkpoint 4: 결과 분석 및 보고 (Result Manager)
단순 슬랙 봇이었던 Agent 4가, 데이터의 무결성을 검증하고(Checkpoint 4) 비즈니스 의사결정(Release/Hold)을 내리는 핵심 게이트웨이(v2 아키텍처)로 진화했습니다.

*   **핵심 개선 로직: 판정 레이어의 완전한 분리**
    *   **1. 5가지 QA 원인 분류 (QA Classification)**
        단순 Fail이 아니라 원인을 명확히 쪼갭니다.
        `(1) 제품 결함, (2) 요구사항 확인 필요, (3) 환경·시뮬레이터 문제, (4) 자동화 코드 문제, (5) 조건 부족 미실행`
    *   **2. Checkpoint 4 (데이터 교차 검증 / VALIDATED)**
        `qa_results.json`과 `report.html`을 교차 검증합니다. 총 건수, 테스트 ID 일치 여부, 상태 불일치 여부를 확인하여 조작이 없음을 증명합니다. 검증을 통과하면 `PASS`가 아닌 `VALIDATED` 상태를 부여하여 "데이터 정합성 확보"의 의미를 명확히 했습니다.
    *   **3. 실제 실행 결과 판정 (`determine_execution_result`)**
        환경 문제든 코드 문제든 실패(Failed/Error)가 1건이라도 있으면 원인 불문 무조건 `FAILED`로 판정합니다. (환경 문제라고 해서 통과시켜주지 않음)
    *   **4. 릴리즈 판정 (`determine_release_decision`)**
        실행 결과가 `FAILED`인 경우는 물론, 실행은 성공(Skipped)했더라도 '요구사항 확인 필요(기획 누락)'이거나 '조건 부족 미실행'이 있으면 찜찜하므로 배포를 막습니다 (`HOLD`).

## 📊 단일 진실의 원천 (Single Source of Truth)
이러한 파이프라인을 거쳐 Agent 4는 외부 연동을 수행하기 전, `reports/agent4_summary.json`과 `reports/checkpoint4_validation.json`을 생성합니다. 
추후 포트폴리오의 웹(HTML) 대시보드는 이 정제된 JSON 데이터만을 바라보게 되며, 이를 통해 수동 입력으로 인한 휴먼 에러나 상태 왜곡(Blocked를 Fail로 표기하는 등)을 원천 차단하는 아키텍처가 완성되었습니다.
