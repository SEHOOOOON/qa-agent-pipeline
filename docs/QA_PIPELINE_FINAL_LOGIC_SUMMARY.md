# 🚀 QA 파이프라인 (Agent 1~4 및 Checkpoint 1~4) 최종 로직 및 아키텍처 명세서

본 문서는 프로젝트 진행 과정에서 고도화된 **Agent(실행 주체)**와 **Checkpoint(검증 게이트)**의 역할, 세부 로직, 판정 기준을 완벽하게 분리하여 정리한 최종 명세서입니다.

---

## 1. Agent (실행 주체) 상세 명세

### 🤖 Agent 1: 요구사항 분석 에이전트 (Requirement Analyst)
*   **역할**: 기획서, 요구사항 명세서를 읽고 누락되거나 모호한 기획의 빈틈을 찾아냅니다.
*   **분류 및 판정 기준 (Ambiguity Detection)**:
    *   **정상**: 모든 UI 동작, 에러 피드백(예: CH05 에러 발생 시 UI 색상 변화 기준)이 명시되어 있는 경우.
    *   **모호성 감지 (기획 누락)**: 에러 상황은 정의되었으나, 이에 따른 구체적인 시스템 피드백이 문서에 명확하지 않은 경우 이를 "요구사항 모호성"으로 분류하여 테스트 설계 전 기획자에게 확인을 요청합니다.

### 🤖 Agent 2: TC 설계 에이전트 (TC Designer)
*   **역할**: 확정된 기획을 바탕으로 실제 자동화 가능한 수준의 구체적인 테스트 케이스(TC)를 설계합니다.
*   **분류 및 판정 기준 (식별자 및 엣지 케이스)**:
    *   **ID 네이밍 룰**: 단순 번호 매기기를 폐기하고, 목적 기반 ID 체계(`TC-MODE-001`, `TC-ENV-000`, `TC-INT-002`)를 강제하여 문서와 코드의 100% 매핑을 유도합니다.
    *   **Boundary(경계값) 테스트 기준**: 사용자가 30°C 초과 조작을 시도할 때 등 명확한 시스템 한계값 도달 시, 단순히 막히는 것을 넘어 방어 로직(Toast 알림, 롤백)이 동작하는지 반드시 TC에 포함시킵니다.

### 🤖 Agent 3: 자동화 테스트 실행 (Test Executor - Pytest & Playwright)
*   **역할**: Agent 2가 설계한 TC를 실제 코드(`test_controller.py`)로 변환하여 브라우저 시뮬레이터에서 실행하고, 원본 데이터를 남깁니다.
*   **핵심 로직 및 기준**:
    *   **메타데이터 강제 주입**: `conftest.py`를 통해 모든 실행 결과에 `run_id`, `tc_id`, `executed_at`, `duration`, `evidence_path(스크린샷)`를 필수로 기록합니다.
    *   단순 Pass/Fail이 아닌, 실패 시 에러 스택트레이스를 포함하여 1차 원시 데이터(`qa_results.json`, `report.html`)를 생성합니다.

### 🤖 Agent 4: 결과 분석 및 보고 (Result Reporting Manager)
*   **역할**: 실행된 테스트 결과를 파싱하여, 단순 성공/실패 여부를 넘어 'QA 원인'을 분류하고 최종 의사결정을 내립니다.
*   **QA 원인 분류 기준 (5 Category)**:
    *   `product_defect` (제품 결함): 명확하게 소프트웨어가 스펙대로 동작하지 않음.
    *   `requirement_review` (요구사항 확인 필요): TC-07처럼 기획서 기준 미비로 인해 맞고 틀림을 Assert 할 수 없음.
    *   `environment_issue` (환경·시뮬레이터 문제): TC-08처럼 제어 명령은 보냈으나 시뮬레이터(백엔드)가 응답하지 않아 Timeout 발생.
    *   `automation_issue` (자동화 코드 문제): DOM 요소 변경 등 Playwright 스크립트 상의 문제.
    *   `not_executed` (미실행): 사전 조건(Pre-condition) 불만족으로 스킵됨.
*   **실행 결과 판정 기준 (`execution_result`)**:
    *   `FAILED`: 원인이 환경(네트워크)이든 결함이든 Failed나 Error가 1건이라도 있으면 무조건 실패.
    *   `INCOMPLETE`: 실패는 없으나 Skipped 등이 존재할 경우.
    *   `PASSED`: 100% Passed.
*   **릴리즈 판정 기준 (`release_decision`)**:
    *   `HOLD`: 실행 결과가 FAILED 거나, 실행이 통과했어도 요구사항 확인(기획 누락) 또는 미실행 항목이 하나라도 존재하면 배포 불가.
    *   `PASS`: 완전한 통과 및 모호성 제로 상태.

## 2. Checkpoint (데이터 검증 게이트) 상세 명세

각 Agent가 다음 단계로 넘어가기 전, 산출물의 **데이터 무결성과 품질**을 컷오프(Cut-off) 하는 검증 룰입니다.

### 🛑 Checkpoint 1: 요구사항 정합성 검증
*   **위치**: Agent 1 -> Agent 2 사이
*   **판정 기준**: 요구사항 명세서 내에 상충되는 룰(예: Rule 2와 모드 변경 규칙의 충돌)이 없는지, 누락된 스펙(모호성)이 해소되었는지 검증합니다. 통과하지 못하면 TC 설계를 시작할 수 없습니다.

### 🛑 Checkpoint 2: TC 커버리지 및 추적성 검증
*   **위치**: Agent 2 -> Agent 3 사이
*   **판정 기준**: 설계된 TC ID가 요구사항 ID와 완벽히 추적(Traceability)되는지 검사합니다. 엣지 케이스, 네거티브 케이스가 일정 비율 이상 포함되지 않으면 자동화 코드 작성 단계로 넘어갈 수 없습니다.

### 🛑 Checkpoint 3: 자동화 스크립트 실행 환경 검증
*   **위치**: Agent 3 실행 직전 (Pre-check)
*   **판정 기준**: 테스트가 실행될 대상 시스템(시뮬레이터, 브라우저) 및 초기 레지스터 상태(가상 기기 16대 정상 로드 등)가 완벽한지 검증(`TC-ENV-000`). 환경 불량으로 인한 가짜 실패(False Negative)를 방지합니다.

### 🛑 Checkpoint 4: 최종 데이터 무결성 검증 (Data Integrity)
*   **위치**: Agent 4 내부 (외부 리포팅 발송 직전)
*   **판정 기준 및 로직**:
    *   **교차 검증**: Agent 3가 만든 `qa_results.json`과 `report.html` 두 파일을 파싱하여, 총 실행 건수, 상태(Pass/Fail/Skip), Test ID가 양쪽에서 100% 일치하는지 비교 검사합니다.
    *   **논리 조합 검증**: 상태와 QA 분류의 조합이 말이 되는지 검증합니다. (예: `Passed`인데 `product_defect`로 분류되면 불일치 에러 발생)
    *   **결과**: 통과 시 테스트 성공을 의미하는 PASS가 아닌, 데이터가 조작되지 않았음을 보증하는 **`VALIDATED`** 상태를 부여합니다.
    *   **차단 룰**: 불일치 발생 시(`BLOCKED`) 외부(Slack/Notion)로 테스트 결과를 발송하는 것을 원천 차단하여, 잘못된 데이터가 보고되는 것을 막습니다.
