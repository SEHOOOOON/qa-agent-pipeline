자기소개·연결실무 경험과 개인 프로젝트가 어떻게 이어지는지

Q11분 자기소개를 해 주세요.
짧은 답

중앙제어 시스템의 기능·연동 검증을 하고 있는 QA 오세훈입니다. 변경 요구사항과 기존 TC를 비교해 검증 범위를 정하고, 화면·API·통신 상태가 맞는지 대조하고, 이슈를 Jira에 남겨 수정 버전에서 다시 확인하는 일을 해 왔습니다. 그 전에는 판매 데이터의 누락·이상값·매핑 오류를 검수하고 반복 조건을 Python·SQL·R로 자동화했습니다.

실무에서 요구사항이 바뀔 때마다 TC를 검토하고 결과를 정리하는 일이 반복돼서, 개인 프로젝트로 이 흐름을 자동화해 봤습니다. 그리고 AI가 만든 결과를 그대로 믿을 수 없어서, 그 결과를 따로 평가하는 도구도 만들었습니다.

조심할 점
  • 실무에서 테스트 전략을 주도했다고 말하지 않습니다. 맡은 범위(검증 범위 정리, 정합성 확인, 이슈 재검증, 일부 자동화)만 말합니다.
Q2왜 이 프로젝트를 만들었나요?
짧은 답

실무에서는 요구사항이 바뀌면 영향받는 TC를 찾고, 시험을 추가하고, 결과를 정리하는 일이 매번 반복됐습니다. 이 반복 작업을 AI와 자동화에 맡기고, 사람은 변경이 맞는지와 결과 검토에 집중할 수 있는지 확인하고 싶었습니다.

근거
  • 실제 회사 자료는 쓰지 않고, 가상 중앙제어 시스템과 예시 요구사항으로 만들었습니다.
Q3데이터 QA에서 소프트웨어 QA로 옮긴 이유는요?
짧은 답

두 일 모두 "기준과 실제 결과가 맞는지 확인하고, 반복되는 확인은 자동화한다"는 점이 같았습니다. 데이터 검수에서는 누락·이상값·매핑을, 소프트웨어 검증에서는 화면·API·통신 상태의 정합성을 봤습니다. 개인 프로젝트도 같은 축에서 요구사항과 실행 결과를 연결한 것입니다.

조심할 점
  • 위 답은 두 일의 공통점입니다. 실제로 옮긴 계기는 본인 경험으로 한 문장 덧붙입니다.

프로젝트1 설계왜 이렇게 나눴는지, 어디까지 자동화했는지

Q4전체 구조를 간단히 설명해 주세요.
짧은 답

입력은 변경 요청, 기존 SRS, 기존 TC입니다. Agent 1이 요구사항을 분석하고, Agent 2가 TC를 설계합니다. 이 두 단계는 AI가 하고, 결과는 프로그램이 원문 값과 대조합니다. Agent 3은 TC의 조작을 제품 연결표로 화면 요소에 연결해 Playwright로 시험하고 원래 상태로 되돌립니다. Agent 4는 규칙 기반으로 결과를 분류해 보고합니다. 마지막으로 공식 TC 등록 여부는 사람이 정합니다.

근거
  • 분석·설계·근거 검토: OpenAI 모델(gpt-6.1-sol, 추론 medium)
  • 화면 요소 연결: 미리 만든 제품 연결표(AI 아님)
  • 결과 분류: 제품 불일치 후보 / 판정 근거 부족 / 환경 문제 / 자동화 실행 문제 / 미실행
Q5추가저장소에 V1과 V2가 있던데, 무엇이 다른가요?
짧은 답

V1은 AI를 호출하지 않고, 미리 만든 산출물로 4단계 흐름과 자동 검사가 맞게 이어지는지 먼저 확인한 시제품입니다. V2(프로젝트1)는 실제 AI 모델이 분석과 설계를 하고, 그 결과를 프로그램 검사와 사람 승인으로 거르는 구조입니다. V1에서 흐름을 검증한 뒤, V2에서 실제 AI의 흔들림을 다루는 쪽으로 넘어갔습니다.

조심할 점
  • V1의 실패 3건은 분류가 맞게 되는지 보려고 일부러 넣은 것입니다. "V1 결과가 FAILED"라는 질문이 나오면 그렇게 설명합니다.
Q6Agent 4는 AI를 안 쓰는데 왜 Agent라고 부르나요?
짧은 답

처음에는 단계별 담당을 Agent 1~4로 나눴습니다. 만들면서 결과 집계와 분류까지 생성형 AI에 맡기는 건 맞지 않다고 판단해 규칙 기반으로 바꿨습니다. 그래서 지금 'Agent'는 AI 모델이라기보다 단계별 책임 단위라는 뜻입니다. 페이지에도 'AI 미사용'이라고 표시했습니다.

근거
  • 지금 버전의 Agent 3은 화면 요소를 AI가 고르지 않습니다. 제품 연결표로 연결하고, 허용된 동작만 코드로 바꿉니다. AI는 근거 검토에만 씁니다.
Q7어디는 AI에게 맡기고, 어디는 프로그램으로 정했나요? 기준이 뭔가요?
짧은 답

문장을 읽고 해석해야 하는 일(요구사항 분석, TC 문장 작성)은 AI에게 맡겼습니다. 값·대상·판정 시점처럼 맞고 틀림이 분명한 것은 프로그램이 엄격하게 검사합니다. 결과 분류와 집계처럼 같은 입력이면 같은 답이 나와야 하는 일도 프로그램이 합니다.

근거
  • 개발 중 같은 요구사항을 단계마다 다르게 읽는 문제가 있어서, 확정된 원문과 시험 내용은 다음 단계가 다시 쓰지 않고 프로그램이 그대로 넘기게 했습니다.
  • 검토 AI가 너무 엄격해 정상 TC가 멈추는 문제도 있어서, 지적을 '치명'(멈춤)과 '경고'(기록하고 진행)로 나눴습니다.
Q8정보 부족과 요구사항 불일치는 어떻게 구분하나요?
짧은 답

시험에 필요한 값이 요청이나 SRS에 없으면 '정보 부족'입니다. 이때는 기대값을 만들지 않고 질문을 남기고, 핵심 범위가 불명확하면 멈춥니다. 반대로 기대값이 원문에 있고, 정상적으로 실행했는데 실제 관찰이 다르면 '제품 불일치 후보'입니다.

근거
  • 잠금 정책이 정해지지 않은 요청: 추측해서 시험하지 않고 질문을 남긴 뒤 멈췄습니다. 이건 실패가 아니라 정상 동작으로 평가했습니다.
  • 알림 색상이 미정인 요청: 확정된 조건만 시험(2건 통과)하고, 색상은 사람 확인 항목으로 넘겼습니다.
  • 잠금 후 온도 버튼이 계속 활성인 사례: 내부 locked 값은 true인데 버튼은 enabled → 불일치 후보로 보고. 결함 확정은 사람이 합니다(Q12).
Q9실행하지 않은 TC는 결과에서 어떻게 처리하나요?
짧은 답

PASS로 세지 않습니다. 미실행·실행 오류·환경 문제는 제품 결과와 따로 분류합니다. 실행한 TC가 모두 통과해도 확인하지 못한 항목이 남으면 사람 검토로 넘깁니다.

근거
  • 환경 점검에서 막혀 회귀 TC가 실행되지 않으면 '판정 근거 부족'으로 분류하고, 다시 실행하도록 보고합니다.
  • 자동화할 수 없거나 검토에서 반려된 TC도 Slack·Notion 보고에서 제품 FAIL과 구분해 표시하는지 내부 시험으로 확인합니다.
Q10공식 TC 등록과 SRS 변경은 왜 사람에게 남겼나요?
짧은 답

자동 검사를 통과했다는 것과 공식 자산으로 등록해도 된다는 것은 다르기 때문입니다. 변경 요청이 승인된 내용인지, 기존 TC를 대체해도 되는지는 조직의 판단이라서 자동화하지 않았습니다. 시스템은 근거와 함께 후보를 만들고, 사람이 SRS 변경·TC 추가·대체·미등록·보류 중에서 고릅니다.

근거
  • 승인되지 않은 변경 요청은 기존 SRS를 덮어쓰지 않습니다. 프로젝트에서는 변경 요청을 '승인 가능한 입력'으로 가정하고, SRS 개정은 제안으로만 만듭니다.
  • 승인 전에 SRS가 바뀌지 않는지는 내부 시험으로도 확인합니다.
  • 실제로 중풍 TC는 시험 통과 뒤에도 바로 등록하지 않았고, 더 상세하게 다시 쓴 TC를 사람이 승인해 TC-V2-002로 등록했습니다.
Q11온도 요청의 필수 시험은 왜 5개인가요? 완전하다고 할 수 있나요?
짧은 답

완전한 정답은 아니고, 이번 평가에서 '꼭 있어야 한다'고 정한 최소 기준입니다. 범위가 바뀌면 양쪽 끝에서 안쪽 값은 설정되는지, 바로 바깥 값은 막히는지를 봐야 해서 냉방 4개가 나오고, 바뀌지 않은 난방은 영향이 없는지 1개를 봅니다.

근거
  • 사람이 정한 규칙: T-1(바뀐 범위의 양 끝 적용), T-2(바로 바깥 값 차단 둘 다 필수, 바뀌지 않은 모드의 차단은 권장), T-5(정해지지 않은 전환 동작은 질문), T-7(한 모드의 경계는 한 TC에), T-8(차단 판정은 값이 그대로인지만).
  • 실제 제품이라면 직접 입력, 저장 후 새로고침, 권한, 통신 지연 같은 시험이 더 필요합니다. 이번 범위는 버튼 조작과 값 확인입니다.
조심할 점
  • '정답'이라는 말 대신 '이번 평가의 필수 시험', '사전에 정한 기대 결과'라고 말합니다.
Q12추가내부값만 보면 되지, 왜 화면까지 Playwright로 확인하나요?
짧은 답

내부값이 맞아도 화면이 다르게 동작할 수 있기 때문입니다. 잠금 요청 실행에서 장비의 내부 잠금 값은 true로 바뀌었는데, 화면의 온도 내림·올림 버튼은 계속 눌리는 상태였습니다. 내부값만 봤다면 통과로 끝났을 문제입니다. 그래서 화면 표시, 장비 카드, 내부값을 따로 확인하고, 이 경우는 결함으로 단정하지 않고 '제품 불일치 후보'로 사람에게 넘겼습니다.

근거
  • 기대값을 바꿔 PASS시키지 않았습니다. 제품의 현재 동작을 기대값으로 복사하지 않는 것이 원칙입니다.
  • 이 실행에서 Slack 1건·Notion 4건을 실제로 전송했습니다. 평소에는 실제 전송 없이 미리보기만 만듭니다.

대표 사례면접에서 먼저 꺼내기 좋은 순서: 복원 누락 → 경계값 누락 → 범위 밖 결함 → 언어

Q13가장 어려웠던 문제와 해결 과정을 말해 주세요. (복원 확인 누락)
짧은 답

온도 시험은 준비 단계에서 운전 모드를 냉방이나 난방으로 바꾸는데, TC의 시험 뒤 확인에는 설정 온도만 있고 모드를 되돌렸는지는 없었습니다. 요청서에 "바꾼 값은 원래대로 돌리고 확인한다"는 조건이 있었는데도 빠졌습니다. 바로 고치지 않고 먼저 같은 요청으로 여러 번 실행해 4번 중 4번 빠지는 것을 확인했습니다. 원인을 따라가 보니 TC 데이터 형식에 '준비 때 바꾼 값'의 복원 확인을 적을 칸 자체가 없어서, 지침에 한 줄을 더 넣는 것으로는 고칠 수 없었습니다. 칸을 추가하고 비어 있으면 자동 검사에서 막도록 바꿨더니, 같은 분석 결과로 설계를 3번 다시 해서 3번 모두 들어갔고, 실제 실행에서도 원래 상태로 돌아왔습니다.

근거
  • 개선 기록 IMP-015. 수정 전: 전체 실행 1번 + 시험 설계만 3번, 모두 누락.
  • 수정: P1 RestoreConfirmation.precondition_indexes 추가, 자동 검사 CP2-023에서 빠지면 차단.
  • 수정 후: 설계 3번 모두 포함, 전체 실행에서 RESTORE_STATUS: RESTORED, Claude 채점 복원 기준 3점 → 4점.
이 사례로 말하고 싶은 것
  • 지침 문장만 고쳐서는 안 되는 문제였고, 반복 횟수를 먼저 확인한 뒤 데이터 형식과 검사 로직을 함께 고쳤다는 점.
Q14AI가 놓친 경계값 시험은 어떻게 찾았나요?
짧은 답

"냉방은 20°C 아래로 못 내려가게, 난방은 그대로" 요청에서 AI가 만든 TC를 프로젝트1의 검토 AI는 통과시켰고, 평가 도구의 채점 AI는 5점 만점을 줬습니다. 제가 결과를 직접 검토해 보니, 아래쪽은 막히는지만, 위쪽은 설정되는지만 봐서 새 최저값 20°C가 실제로 설정되는지와 31°C가 막히는지가 빠져 있었습니다. 그래서 "범위 끝은 설정되는 값과 막히는 값을 각각 시험한다"는 규칙을 TC 작성 지침, 자동 검사, 평가 도구의 필수 시험 대조 세 곳에 넣었고, 이후 8번 모두 필수 시험 5개가 들어갔습니다.

근거
  • 처음 TC(10-15 실행): 필수 5개 중 3개. 채점 AI 점수 5점 → 프로그램 대조로 바꾼 뒤 같은 TC가 2점.
  • 필수 시험 목록은 이 누락을 찾은 뒤에 만들었습니다. 그 뒤 실행부터는 목록을 실행 전에 정해 두고 대조했습니다.
조심할 점
  • 처음 TC에 대해서는 "실행 전에 정한 기준"이라고 말하지 않습니다. 실행 뒤 사람이 검토하다 찾은 것입니다.
Q15추가변경 범위 밖에서 결함을 발견하면 어떻게 하나요?
짧은 답

그 변경의 시험 범위를 넓히지 않고, 따로 기록합니다. 온도 실행에서 당시 넣었던 '난방 15°C 막힘' 시험이 제품의 기존 결함을 찾았습니다. 난방 하한은 16°C인데 15°C까지 내려갔고, 예상 목록에 없던 결과였습니다. 다만 이번 요청은 냉방 범위만 바꾸는 것이라, 난방은 '영향이 없는지' 1개만 보도록 기준을 정리했습니다. 난방 끝을 보려면 15°C와 31°C를 둘 다 봐야 해서, 한쪽만 넣는 것도 맞지 않았습니다. 결함은 변경 범위 밖 기존 결함으로 기록해 두었습니다.

조심할 점
  • "결함을 찾은 시험을 기준에서 뺐다"로 들리지 않게, 기준을 바꾼 이유(변경 범위)와 결함을 따로 기록한 사실을 함께 말합니다.
Q16TC 제목이 중국어로 나온 건 어떻게 된 일인가요?
짧은 답

풍량 대표 실행에서 TC 제목이 중국어로 생성됐는데, 검토 AI와 채점 AI 모두 놓쳤고 제가 발견했습니다. 사람이 읽는 문장에 한자나 일본 문자가 섞이면 자동 검사에서 막고 다시 쓰게 했습니다. 요구사항 원문을 그대로 옮긴 부분은 예외로 둡니다.

근거
  • 그 뒤 반복 실행 설계에서는 다른 언어가 섞인 경우가 없었습니다. 저장된 설계 8개를 새 검사로 다시 돌렸을 때 풍량만 걸렸습니다(오탐 0).
  • 개선 기록 IMP-018: 검사 범위를 분석·설계 문장과 채점 이유까지 넓혔고, 새 실행에서의 확인은 아직 남아 있습니다.
  • 한국어 문장 구분자(・, ー)를 일본어로 잘못 막던 오탐도 찾아 고쳤습니다.

Q17프로젝트2는 왜 만들었나요?
짧은 답

프로젝트1이 한 번 잘 되는 것보다, 여러 요청에서 필요한 검사를 빠뜨리지 않는지가 중요했습니다. 그리고 시험이 실패한 것과 에이전트가 실수한 것은 다릅니다. 이 셋을 구분하려고 만들었습니다.

Q18추가평가 도구 자체가 틀린 적은 없나요?
짧은 답

있습니다. 평가 도구도 시험 대상으로 봤습니다. 대표적으로 전원 실행에서 복원 확인이 실제로는 있었는데 3점이 나왔습니다. 원본을 보니 비교할 원문이 평가 자료에 직접 전달되지 않아 채점 AI가 볼 수 없었습니다. 전달 방식을 고친 뒤 5점이 됐습니다. 점수가 이상하면 에이전트보다 먼저 평가 자료부터 확인하는 순서를 개선 절차에 넣었습니다.

근거
  • IMP-004: 비교할 원문을 평가 자료에 직접 넣도록 수정(3점 → 5점).
  • IMP-017: Claude 채점이 일부 기준에만 답한 경우를 프로그램이 잡아 1번 다시 요청하고, 시도별 기록을 남기게 했습니다.
  • 개선 절차의 두 번째 단계가 "맞는 감점인지 원본과 대조"입니다. 평가자가 잘못 판단한 것이면 평가 도구를 고칩니다.
Q19평가 기준은 몇 개인가요? 26개라더니 5개는 왜 점수가 없나요?
짧은 답

기준은 26개를 설계했고, 대표 요청 5개에서 실제로 점수가 나온 건 21개입니다. 프로젝트1의 결과물 네 가지(분석 결과, TC, 실행·복원 기록, 보고서)마다 "이 결과물이 지켜야 할 것"을 질문으로 만들었습니다. 0~5점이고 4점 이상이 통과, 3점 이하는 실패입니다.

빈 5개는 이유가 다릅니다. C02 '역할을 넘는 지시를 따르지 않는가'는 대표 요청에 그런 지시가 없어서 시험할 상황이 없었습니다. 판정하려면 그런 지시를 일부러 넣은 요청을 만들어야 합니다. 단계 연결 4개는 요청 조건이 시험과 보고까지 끊기지 않는지 보는 기준인데, 프로젝트1의 핵심 주장과 직결돼 가장 중요하다고 보지만 채점 방법을 아직 완성하지 못했습니다. 그래서 지금 결과는 '단계별 품질은 확인, 단계 사이 연결은 아직'이라고 말합니다.

조심할 점
  • "26개 기준으로 평가했다"고 말하지 않습니다. "21개로 채점했고, 5개는 이런 이유로 다음 단계"라고 먼저 말합니다.
근거
  • 개수·값·기록 대조처럼 셀 수 있는 기준은 프로그램이 채점합니다(예: 필수 시험이 TC에 다 있는가, 보고서 개수가 실행 기록과 같은가).
  • A4-02(실패 원인 분류)는 실패가 나온 온도 요청 1건에서만 판정됐습니다.
Q20기준마다 중요도가 다른데 같은 비중으로 평균 내도 되나요?
짧은 답

평균은 한눈에 보기 위한 요약이고, 실제 판단은 기준별 통과·실패로 봅니다. 예를 들어 온도 요청은 평균 4.86이지만, 복원 확인 1개가 실패(3점)로 남아 개선 대상이 됐습니다.

개선 방향으로 덧붙이면
  • 필수 시험 누락, 실행하지 않은 항목의 PASS 처리처럼 하나라도 있으면 안 되는 기준은 '필수 관문'으로, 설명의 충분성 같은 기준은 '품질 점수'로 나누는 게 더 맞다고 봅니다. 지금은 나누지 않았습니다.
Q21사람 기준을 혼자 만들었는데 객관적이라고 할 수 있나요?
짧은 답

객관적인 정답이라고 하지는 않습니다. 기준을 만든 제가 혼자 판단한 것이라, 이번 평가 범위의 기준선으로 썼습니다. 다른 QA와의 일치도는 확인하지 않았고, 이게 가장 큰 한계 중 하나입니다.

근거
  • 대신 사람 판단도 기록으로 남겼습니다. 애매한 경우는 질문 목록으로 정리해 결정(H-1~H-6)을 남기고, 결정이 바뀌면 이전 실행과 직접 비교하지 않았습니다.
실무라면
  • 두 명 이상이 독립적으로 판단한 뒤 차이를 맞추는 과정을 넣겠습니다.
Q22실행 뒤에 기준을 바꾼 적이 있나요? 그럼 점수는 어떻게 처리했나요?
짧은 답

있습니다. 온도 요청의 난방 시험을 사람 결정으로 두 번 바꿨습니다(H-5: 16°C에서 15°C 시도 → 막힘, H-6: 바뀌지 않은 난방은 16°C 설정 1개만). 점수는 그 실행 당시의 기준으로 매긴 그대로 두고, 기준이 바뀐 뒤의 실행과는 직접 비교하지 않았습니다.

근거
  • 점수표의 온도 실행(10-23)은 당시 기준(H-5)으로 필수 5/5였고, 권장 시험(난방 31°C 막힘)이 없어 4점이었습니다.
  • 처음 TC(10-15)는 필수 시험 목록이 생기기 전에 실행됐습니다. 지금 목록으로 보면 5개 중 3개인데, 이건 실행 뒤 비교라고 밝혀 두었습니다.
조심할 점
  • "모든 기준을 실행 전에 정했다"고 말하지 않습니다.
  • 난방 결함 이야기는 숨기지 말고 먼저 꺼냅니다(Q15).
Q23점수가 거의 다 5점인데, 기준이 느슨한 것 아닌가요?
짧은 답

저도 그 점이 걱정이라 5점을 그대로 믿지 않았습니다. 처음 사람이 대조한 15개 중 4개가 AI가 후하게 준 점수였고, 그 4가지 유형을 고쳤습니다. 지금 점수표는 그렇게 고친 뒤의 결과입니다. 오히려 보여 드리고 싶은 건 점수보다 그 과정에서 찾은 누락과 오판입니다.

근거
  • 후한 점수 4가지: 범위 한쪽 끝만 시험해도 만점 / 조작과 확인을 한 줄에 섞어도 만점 / 고쳐 쓸 기존 TC가 있는데 새로 만들어도 만점 / 다룰 일이 없던 기준에도 만점.
Q24프로젝트2가 프로젝트1에 맞춰진(과적합된) 평가기는 아닌가요?
짧은 답

그 가능성은 남아 있습니다. 기준을 고친 뒤 새로 실행한 결과로 다시 확인했지만, 요청 종류는 처음과 같은 대표 요청 4개였습니다. 새로운 종류의 요청(여러 장비, 새 기능 추가)으로는 아직 확인하지 않았습니다. 그래서 '개선 후 같은 종류의 요청에서 다시 확인했다'까지만 말합니다.

평가 AI채점 모델과 독립성

Q25채점 AI는 어떻게 골랐나요? 다른 회사 모델이면 독립적인가요?
짧은 답

같은 자료를 OpenAI와 Claude로 채점해 사람 판단 12개와 비교했습니다. OpenAI가 12/12, Claude 기본 설정은 같은 입력에서도 10~11/12로 흔들렸고, Claude를 깊게 생각하는 설정으로 바꾸니 12/12였습니다. 정확도만 보면 차이가 없어서, 생성과 같은 모델로 채점하면 같은 부분을 함께 놓칠 수 있다는 점을 고려해 Claude를 기본으로 정했습니다. 다만 회사가 다르다고 독립성이 보장되지는 않아서, 프로그램 대조와 사람 확인을 같이 씁니다.

근거
  • 처음 경계값 누락을 놓친 원인을 확인해 보니, 같은 회사 모델이라서라기보다 채점 기준이 막연해서였습니다. 기준을 고친 지금의 OpenAI도 그 누락을 잡았습니다.
꼭 먼저 말할 것
  • 포트폴리오의 대표 요청 5개 점수표는 Claude로 바꾸기 전, 생성과 같은 OpenAI 모델(gpt-6.1-sol)로 채점한 결과입니다. 페이지에도 그렇게 밝혀 두었습니다.
Q26채점 AI가 틀리면 최종 판정은 누가 하나요?
짧은 답

사람이 합니다. 채점 AI는 사람이 먼저 볼 곳을 찾는 도구로 씁니다. 점수만으로 합격을 정하지 않고, AI 점수가 원문과 맞는지 다시 확인해 틀리면 채점 기준을 고칩니다.

근거
  • Claude가 일부 기준에만 답하거나 이유를 한국어가 아닌 말로 쓰면 1번 다시 요청하고, 처음 실패도 기록에 남깁니다(IMP-017).
Q27추가AI 모델 설정은 어떻게 했나요? 같은 입력에 다른 답이 나오는 건요?
짧은 답

프로젝트1의 분석·설계와 근거 검토는 OpenAI gpt-6.1-sol에 추론 단계 medium, 프로젝트2의 채점은 Claude Sonnet 5.5에 생각 깊이 high를 씁니다. 같은 입력에도 답이 달라질 수 있다는 걸 전제로 설계했습니다. 맞고 틀림이 분명한 값은 프로그램이 대조하고, 틀리면 한 번만 다시 쓰게 하고, 바뀐 부분은 반복 실행으로 다시 나오는지 확인합니다.

근거
  • Claude 기본 설정은 같은 입력에서 판정이 흔들려(10~11/12) 깊게 생각하는 설정으로 바꿨습니다.
  • Claude Haiku는 긴 한국어 자료에서 출력 한도를 넘겨 답을 끝내지 못해 후보에서 뺐습니다.

반복·안정성몇 번을 돌렸고, 무엇이 같았는지

Q283번, 8번 반복으로 안정적이라고 할 수 있나요?
짧은 답

통계적으로 안정적이라고는 하지 않습니다. 고친 문제가 다시 나오는지 확인하는 수준입니다. 도구 자체에도 "한 묶음의 반복이며 통계적 보장이 아님"이라고 남기게 했습니다.

근거
  • 온도 기존 TC 처리는 8번 중 1번 흔들려 지켜보는 중입니다(IMP-016).
Q29반복할 때 조건은 같았나요? "같은 결과"는 문장까지 같다는 뜻인가요?
짧은 답

같은 요청, 같은 분석 결과, 같은 프로젝트1 버전으로 실행했고, 실행마다 새로 시작합니다. "같다"는 건 문장이 같다는 뜻이 아니라, 필수 시험이 다 있는지, 기존 TC를 맞게 처리했는지, 화면·카드·내부값 세 곳을 확인하는지, 바꾼 값마다 복원 확인이 있는지 같은 조건이 같다는 뜻입니다.

근거
  • 첫 TC가 자동 검사에서 막혀 한 번 더 쓴 경우: 모드·온도(고치기 전) 6번 중 4번. 다시 쓴 TC는 모두 통과했습니다.

역할·보안·비용무엇을 직접 했는지, 실무라면 무엇을 지켜야 하는지

Q30코드는 직접 짰나요? 본인이 한 일은 뭔가요?
짧은 답

코드 구현은 AI 코딩 도구를 활용했습니다. 제가 직접 한 것은 요구사항과 검증 기준 정의, 범위 규칙과 사람 결정, 대표 시나리오 구성, 결과 검토와 누락 발견, 개선 방향 결정입니다. 만든 코드는 실행 결과와 자동 시험으로 확인했습니다.

근거
  • 경계값 누락, 중국어 제목, 채점 AI의 후한 점수 4가지는 제가 결과를 검토하다 찾았습니다.
  • 내부 자동 시험: 프로젝트1 약 2,500개, 프로젝트2 약 1,000개.
조심할 점
  • AI 코딩 도구 사용을 숨기지 않습니다. 대신 "무엇을 확인하고 판단했는가"를 구체적인 사례로 답합니다.
Q31추가내부 자동 시험 2,500개는 무엇을 검사하나요?
짧은 답

제품을 시험하는 TC가 아니라, 파이프라인 자체가 약속을 지키는지 검사하는 시험입니다. 예를 들어 미실행이나 자동화 불가 TC가 보고서에서 제품 FAIL과 섞이지 않는지, 제품 결과가 통과든 불일치든 복원 확인은 따로 판정되는지, 사람 승인 전에 SRS가 바뀌지 않는지, 잠금 화면 표시를 내부값에 기대지 않고 실제 화면에서 읽는지 같은 것들입니다.

조심할 점
  • "테스트 2,500개를 만들었다"보다 "파이프라인이 지켜야 할 규칙을 시험으로 고정했다"로 말합니다. 제품 TC 수와 섞지 않습니다.
Q32추가회사 자료를 외부 AI에 보내도 되나요? 보안은 어떻게 했나요?
짧은 답

이 프로젝트는 실제 회사 자료를 쓰지 않고 가상 제품과 예시 요구사항만 썼습니다. 그래도 프로젝트1의 OpenAI 호출은 응답을 저장하지 않는 설정(store=False)으로 보내고, API 키는 환경변수에서만 읽어 저장소에 남기지 않습니다. 공개한 실행 증거에서도 키, Slack Webhook, Notion 자격정보, 로컬 경로를 뺐습니다.

실무라면
  • 회사 자료를 외부 AI에 보내기 전에 사내 보안 정책부터 확인하고, 필요하면 민감 정보를 빼거나 사내에서 승인된 모델만 쓰는 방식으로 하겠습니다.
Q33비용은 얼마나 들었고, 어떻게 통제했나요?
짧은 답

대표 요청 1건을 분석부터 채점까지 돌리면, OpenAI로 채점하던 때는 약 1~1.6달러, 지금 설정(Claude 채점)으로는 약 2달러(추정)입니다. 유료 호출이 있는 명령은 기본이 미리보기라서, 실제로 돌리기 전에 호출 수와 다시 요청하는 상한, 추정 비용을 먼저 보고 승인한 범위에서만 실행했습니다. 숨은 자동 재시도는 두지 않았습니다.

조심할 점
  • 사람의 검토 시간을 얼마나 줄였는지는 측정하지 않았습니다. "비용 대비 효과가 있다"고는 말하지 않습니다.

한계·다음 단계먼저 말하면 신뢰가 올라가는 부분

Q34이 프로젝트의 한계는 뭔가요?
짧은 답
  • 가상 제품, 장비 1대, 기존 기능을 바꾸는 요청만 다뤘습니다.
  • 필수 시험을 프로그램으로 대조하는 건 온도 범위 요청에만 있습니다.
  • 설계한 26개 기준 중 5개는 아직 판정 전입니다(단계 연결 4개, 역할을 넘는 지시 1개).
  • 사람 대조는 27개로 적고, 저 혼자 판단했습니다.
  • 새 종류의 요청으로 독립 검증을 하지 않았습니다.
  • 대표 요청 점수는 생성과 같은 모델로 채점했습니다.
Q35추가그럼 실무에 바로 쓸 수 있나요?
짧은 답

도구를 그대로 쓰기는 어렵습니다. 실제 제품에 연결하지 않았고, 사람의 시간을 얼마나 줄였는지도 측정하지 않았습니다. 대신 바로 가져갈 수 있는 건 방식입니다. 범위가 바뀌면 양 끝을 설정과 막힘으로 각각 시험하는 규칙, 실행하지 않은 항목을 PASS로 세지 않는 집계, 준비 때 바꾼 값까지 복원을 확인하는 TC 형식, 공식 등록은 사람이 하는 승인 단계는 지금 실무 TC 검토에도 바로 쓸 수 있습니다.

Q36더 한다면 무엇을 하겠습니까?
짧은 답
  • 대표 요청 5개를 Claude로 다시 채점하고 반복 측정해, 같은 모델 채점 문제와 반복 결과를 함께 정리하겠습니다.
  • 장비 여러 대를 한 번에 제어하는 요청, 새 기능 추가 요청으로 범위를 넓혀 기준이 그대로 통하는지 보겠습니다.
  • 필수 관문과 품질 점수를 나누고, 단계 연결 기준 4개를 판정하겠습니다. 역할을 넘는 지시를 일부러 넣은 요청도 만들어 C02를 시험하겠습니다.
