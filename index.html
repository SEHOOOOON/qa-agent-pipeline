멀티 에이전트 QA 흐름

01 · 이 프로젝트를 만든 이유

QA 경험을
반복 가능한 기준으로

중앙제어 QA에서 축적한 판단 기준을 매번 개인의 기억과 경험에만 의존하지 않고, 요구사항 정제부터 실행 결과 보고까지 동일하게 적용하기 위해 시작했습니다.

!

반복해서 마주한 문제

  • 같은 요구사항도 검토자에 따라 테스트 범위가 달라짐
  • 머릿속 QA 기준을 매번 TC에 다시 풀어내야 함
  • AI가 요구사항에 없는 기대결과를 그럴듯하게 확정함
  • 모호한 TC와 잘못된 분류가 다음 단계로 전파될 수 있음
✓

프로젝트가 선택한 방식

  • 개인의 QA 기준을 공통·도메인·기능별 규칙으로 구조화
  • 각 Agent는 정해진 형식으로 단계별 결과물을 생성
  • 각 결과물은 QA Checkpoint에서 근거와 품질을 확인
  • 기준을 충족한 결과만 다음 Agent와 자동화 실행으로 전달
핵심 목표AI가 많은 TC를 만드는 것이 아니라, 요구사항부터 실행 결과까지 같은 QA 판단 기준이 끊기지 않도록 유지하고 AI의 추측이 다음 결과물로 전파되는 것을 구조적으로 줄이는 것입니다.

03 · 단계별 QA Checkpoint

통과한 결과만
다음 단계로 전달

Checkpoint는 별도의 AI 이름이 아니라, 각 Agent 결과가 다음 단계로 넘어갈 수 있는지를 판단하는 품질 기준과 검사 절차입니다.

CHECKPOINT 01

요구사항 충분성

확정 정보, 추정 정보와 정보 부족이 구분됐는지 확인합니다.

근거 출처 · 테스트 가능 범위 · 제외 항목
전체 / 일부 / 확인 후 진행
CHECKPOINT 02

TC 품질 적합성

추측성 기대결과, 모호한 표현, 독립 실행성과 자동화 가능성을 확인합니다.

명시적 Assert · Setup/Cleanup · 추적성
승인 / 수정 / 범위 제외
CHECKPOINT 03

실행 결과 신뢰성

환경 점검, 상태 초기화, UI·Register Assert와 실행 증거를 확인합니다.

Pre-check · Snapshot · Screenshot · 유효성
유효 / 재실행 / 환경 확인
CHECKPOINT 04

보고 결과 일관성

실행 수치, 실패 분류와 외부 보고 내용이 일치하는지 확인합니다.

집계 일치 · 분류 근거 · 후속 조치 · 권고안
보고 / 재집계 / 사람 검토
04 · QA 기준

3단계로 적용하는
테스트 설계 기준

공통 QA 기준 위에 중앙제어 도메인 기준을 더하고, 마지막으로 기능별 기대결과와 자동화 가능성을 구체화합니다.

1단계

공통 QA 기준

정상·예외·경계값·상태 변경·회귀 영향·정보 부족을 확인합니다.

2단계

중앙제어 도메인 기준

모드, 통신, 알람, Lock, 다중 장비와 UI·Register 정합성을 확인합니다.

3단계

기능별 품질 기준

적용 조건, 기대결과, Pass/Fail과 자동화 가능 여부를 정의합니다.

요구사항에 없는 값은 제외근거 없는 값은 Pass/Fail 기준으로 사용하지 않습니다.
각 TC는 독립 실행Initial State, Setup과 Cleanup을 포함합니다.
명시적 Assert로 판정AI 의견이 아니라 기대값과 실제값의 비교로 결정합니다.
05 · Checkpoint 2 상세 사례

TC 초안을 반려하고
검증 가능한 범위로 수정

요구사항에 없는 온도 표시 문구가 TC 기대결과로 들어간 사례를 검토하고, 확인 가능한 UI·Register 항목만 승인하는 흐름입니다.

일부 범위 진행

확정 정보와 정보 부족 분리

  • 확정: FAN 모드에서 온도 버튼 비활성화
  • 확인 필요: 온도 표시 문구
  • 확인 필요: setTemp 처리 방식
테스트 가능:
  - FAN 모드 변경
  - 온도 버튼 비활성화
확인 필요:
  - 온도 표시 문구
  - setTemp 처리 방식
초안

근거 없는 기대결과 포함

요구사항에 없는 "---" 표시가 기대결과로 작성됐습니다.

화면 기대결과:
  mode = "FAN"
  temperature = "---" # 근거 없음
하부 기대결과:
  devices[id].mode = "FAN"
수정 요청

Checkpoint 2 판정

  • 정보 부족 항목을 Assert로 사용
  • Source ID 없는 문자열 검증
  • Setup/Cleanup 누락
판정: 수정 후 재검토
수정:
  - "---" Assert 제외
  - 초기 상태와 Cleanup 추가
범위 승인

검증 가능한 항목만 승인

  • UI: FAN 표시, 온도 버튼 disabled
  • Register: mode == FAN
  • 제외: 표시 문구, setTemp 정책
승인:
  ui.mode = "FAN"
  ui.temp_buttons_disabled = true
  register.mode = "FAN"
제외:
  temperature_text
  setTemp_policy
실행 가능

승인된 Assert만 코드로 연결

정보 부족으로 제외된 값은 Playwright 코드에 포함하지 않습니다.

expect(mode_badge).to_have_text("FAN")
expect(temp_up).to_be_disabled()
mode = page.evaluate(
  "() => window.__vccs.devices[0].mode"
)
assert mode == "FAN"
